                              │

                              ├──< inseminations ──> animals (бык)
                              ├──< milk-tests        контрольные дойки

organizations ──< data-submissions ──> media   (исходный файл и протокол ошибок)
                                   ──> animals (записи пакета: кого касается проверка)

## Animal ●

Центральная сущность. Организована вкладками — они же вкладки карточки
в интерфейсе.

| Вкладка | Состав |
| --- | --- |
| **Общие данные** | GUID, индивидуальный номер и его формат, кличка и её латиница, альтернативные идентификаторы (бирка, чип RFID и дата чипирования, инвентарный, международный, ISO, марка и номер ГПК), пол, тип, состояние, возрастная группа, дата рождения, порода и кровность, породы-улучшатели с долями крови, масть, группа крови, назначение, владелец, стадо, автор записи, уровень достоверности и дата его подтверждения, флаги публичности, признак «выставлено на продажу», фото, примечание |
| **Оценка** | ИПЦ с прогнозом, достоверностью R,% и процентилем; служебный ранг `ipcRank`; продуктивные признаки; воспроизводство; здоровье; 18 линейных признаков экстерьера и 3 композита |
| **Фенотип** | сводка для таблицы поиска (удой, жир, белок в % и кг, сумма жира и белка), служебный ранг `summary.milkRank` и массив лактаций |
| **Происхождение** | отец и мать связями, линия и семейство, категория племучёта, основание регистрации (по происхождению / по продуктивности), класс, текстовая родословная, коэффициент инбридинга |
| **Генетика** | CVM, BLAD, DUMPS, генотипы молочных белков (каппа-казеин, бета-казеин, бета-лактоглобулин), гаплотипы, ДНК-тесты |
| **Движение** | поступление и предыдущее хозяйство, выбытие с причиной и хозяйством выбытия, архивация с причиной |

Поля чипирования (`altIds.chipNumber`, `altIds.chipDate`) лежат во вкладке
«Общие данные» вместе с остальными идентификаторами, а не в «Движении»:
чип — это способ опознать животное, а не событие его перемещения.

### Идентификация

- **GUID** (`uuid`) — присваивается автоматически при создании, глобально
  уникален, неизменяем, не зависит от номера внутри хозяйства. Заготовлен
  под передачу в ФГИАС ПР.
- **Транслитерация клички** по ГОСТ 7.79-2000 (ISO-9) в поле `nameLatin`.

**Индивидуальный номер** проверяется по формату — `src/lib/animal-id.ts`,
таблица `ID_RULES`:

| Формат | Шаблон | Примечание |
| --- | --- | --- |
| `rf` | 6–15 цифр, допускается суффикс вида `.00` | национальный номер РФ |
| `icar` | 3 буквы породы + 2–3 буквы страны + 8–12 цифр | Interbull, `HOLUS123456789` |
| `usa` | `HO` + `USA`, `CAN`, `NLD` или `DNK` + 7–12 цифр | одно правило на четыре страны, хотя подпись говорит только о США |
| `can` | `HOCAN` + 7–12 цифр | частный случай предыдущего правила |
| `deu` | `DEHOL` + ровно 7 цифр | Германия |
| `internal` | 1–32 символа без пробелов | внутрихозяйственный |

Функция `luhnValid` реализована и вызывается, но ни одно правило в `ID_RULES`
не выставляет флаг `luhn` — контрольная сумма сейчас не проверяется ни для
одного формата. Включение сводится к правке таблицы правил.

### Логические проверки

- отец и мать не могут быть одним и тем же животным;
- дата рождения не в будущем;
- потомок не может родиться раньше родителя. Проверка выполняется только
  тогда, когда затронуты сама дата рождения или связи `father` / `mother`.
  Иначе запись с уже накопленным противоречием стала бы нередактируемой
  целиком: нельзя было бы поправить даже кличку, пока не исправлены даты предка;
- инбридинг выше 25% — флаг `inbreedingNeedsApproval` («требует ручного
  подтверждения»). Порог 6,25% в серверных проверках не участвует: это только
  предупреждение в интерфейсе карточки;
- `uuid` присваивается при создании, если не задан явно;
- `author` заполняется по сессии при создании;
- `lastEditUser` и `lastEditTime` заполняются автоматически при каждом изменении.

Константа `MIN_DAM_AGE_MONTHS = 18` объявлена, но нигде не используется —
проверки возраста матери на дату отёла в коде нет.

### Служебные поля сортировки

| Поле | Зачем |
| --- | --- |
| `ipcRank` | пара к `ipc` |
| `summary.milkRank` | пара к `summary.milkYield` |

Оба поля индексированы, имеют `defaultValue = −1 000 000` и заполняются хуком
`beforeChange`: если значение основного поля — число, ранг равен ему, иначе
остаётся минимумом. Это обход поведения PostgreSQL, который при
`ORDER BY … DESC` ставит NULL первыми: без ранга животные без оценки
вытесняли бы из начала списка тех, у кого оценка есть. По возрастанию NULL
и так уходят в конец, поэтому текстовым полям служебная пара не нужна.

Тем же хуком считается `summary.fatProteinSum` — сумма жира и белка в кг,
если заданы оба слагаемых.

### Индекс племенной ценности ●

Поле `ipc` в карточке — оценка, привезённая извне: её присылает расчётный
центр, система её показывает. Рассчитанный системой индекс живёт отдельно,
в `index-values`, по строке на пару «животное + профиль»: значение зависит
от набора весов, а наборов у одного животного столько, сколько их завели
хозяйства.

Вместе со значением хранятся снимок весов, версия базы сравнения и дата
расчёта — иначе через полгода число в выпущенном документе будет нечем
объяснить. Пересчёт идёт хуками: изменилось животное — его значения по всем
профилям, изменились веса — профиль по всей книге. Полный прогон —
`npm run backfill:index`.

База сравнения — коллекция `index-bases`: средние и стандартные отклонения
признаков, по одной записи на версию. Действующая одна, прежние остаются
историей: рядом с каждым значением записана версия, и без неё старое число
не объяснить. Пока своей базы нет, используется заимствованная из кода.

Подробности расчёта и границы решения — `docs/indeks-plemennoy-cennosti.md`.

### Чего не хватает для сертификатов ◐

Раздел племенной книги, номер в племенной книге, страна рождения, номер РСН,
способ получения потомка (естественное осеменение / ЭКО / эмбриотрансфер),
селекционер отдельно от владельца. Поля ГПК (`altIds.gpkMark`,
`altIds.gpkNumber`) в модели уже есть. Полный разбор —
[sertifikaty-audit.md](sertifikaty-audit.md).

## Pedigree ●

Родословная строится не отдельной таблицей, а обходом связей `father` / `mother`.
Задачи две, и они разведены по разным модулям.

| Модуль | Что делает |
| --- | --- |
| `src/lib/pedigree.ts` | строит дерево на три ряда предков для карточки и печатных документов, размечает узлы |
| `src/lib/ancestry.ts` | разбирает родословную вглубь и считает коэффициент инбридинга |

**Дерево на три ряда предков:** О/М → ОО/МО/ОМ/ММ → восемь узлов третьего ряда.
Код узла читается справа налево: ОМ — отец матери, МОО — мать отца отца.
Предки, заведённые карточками, кликабельны; текстовые предки показываются,
но никуда не ведут.

### Разбор вглубь и коэффициент инбридинга

Расчёт живёт в `src/lib/ancestry.ts`, функция `analyzeAncestry`. Прежняя
`wrightInbreeding` из `pedigree.ts` удалена. Глубина обхода —
`ANCESTRY_DEPTH = 9` поколений, а не 5.

Дерево на девять колен не рисуют: девятое колено — это 512 клеток, из которых
в реальной базе заполнены единицы. И вопрос на глубине уже другой: три-четыре
колена отвечают «кто родители», дальше спрашивают «чья кровь в животном»
и «откуда инбридинг», а это список с числами, а не картинка.

Два решения делают такую глубину возможной:

- **загрузка по колену, а не по узлу.** Предки образуют граф, а не дерево:
  один бык встречается в родословной десятки раз, но в базе он один. Колено
  забирается целиком одним запросом `id in (…)`, поэтому девять колен стоят
  девять запросов, а не тысячу;
- **кратности вместо путей.** Число путей до предка растёт экспоненциально,
  перечислять их нельзя. Вместо списка хранится счётчик «сюда ведёт 6 путей
  длиной 7». Все нужные формулы — суммы по путям, и с кратностями они
  считаются так же точно.

Результат — `AncestryReport`:

| Поле | Значение |
| --- | --- |
| `ancestors` | таблица предков, отсортированная по доле крови |
| `coi` | коэффициент инбридинга по Райту, %, — сумма вкладов из таблицы |
| `coverage` | заполненность по коленам: известно предков из возможных `2^n` |
| `deepest` | самое глубокое колено, где нашёлся хотя бы один предок |
| `totalDistinct` | всего различных предков во всей родословной |

Строка предка (`AncestorRow`) содержит `generations` (колена, в которых он
встречается), `occurrences` (число путей к нему), `bloodShare` (доля крови, %),
`onBothSides` (встречается и со стороны отца, и со стороны матери) и
`coiContribution` (вклад в коэффициент инбридинга, %).

**Формула Райта:**

```
F = Σ (1/2)^(p+q+1) · (1 + F_A)
```

Собственный инбридинг общего предка `F_A` считается не по сохранённому полю,
а отдельным обходом — тем же алгоритмом и только для предков, которые
действительно встречаются с обеих сторон. Их обычно единицы, а полный расчёт
для каждого узла превратил бы отрисовку карточки в вычислительную задачу.

Контрольные значения для проверки — именно коэффициенты инбридинга потомка,
а не коэффициенты родства родителей (те вдвое больше):

| Пара родителей | F потомка |
| --- | --- |
| родитель × потомок | 0,25 |
| полные сибсы | 0,25 |
| двоюродные | 0,0625 |

Порог 6,25% — предупреждение в интерфейсе карточки. Единственная серверная
реакция — флаг `inbreedingNeedsApproval` при значении выше 25%.

### Разметка источников инбридинга

Дерево отвечает на вопрос «откуда взялся инбридинг», а не только «какой он».

| Состояние | Как показано | Что означает |
| --- | --- | --- |
| Общий предок | сплошная заливка своим цветом и точка | встречается и у отца, и у матери — даёт вклад в COI |
| Повтор в одной стороне | пунктирная рамка того же цвета | инбредным является родитель, на инбридинг потомка не влияет |
| Путь к предку | соединители окрашены в цвет группы | видна «петля» инбридинга |
| Не подтверждено | оранжевая точка у кода | у предка уровень достоверности ниже 2 |
| Обрыв ветви | пунктирная серая рамка | предка нет в системе |

Каждой группе повторяющихся предков достаётся свой цвет из палитры вне
фирменной зелёной гаммы — чтобы цвет не читался как «хорошо / плохо».
При наведении на узел подсвечиваются все вхождения того же животного
и пути к ним, остальное дерево приглушается.

**Геномный инбридинг F_ROH** ◐ — см. [genomnyy-konveyer.md](genomnyy-konveyer.md).

## Phenotype Record ●

Фенотип — не одно поле, а четыре потока фактов, каждый со своей датой,
источником и автором.

| Коллекция | Что фиксирует |
| --- | --- |
| `calvings` | номер отёла, дата, результат (тёлка / бычок / двойня / мертворождение / аборт), дойные дни, дата запуска, лёгкость отёла, масса телёнка |
| `inseminations` | дата, бык, тип семени, метод, число доз, номер попытки, техник, результат, дата проверки стельности; привязка к номеру отёла |
| `milk-tests` | дата, номер лактации, суточный удой, жир и белок в %, соматические клетки, лаборатория, источник |
| `health-events` | тип, дата, тяжесть, период, описание, кто зафиксировал, флаг исключения из аналитики |

Разделение принципиально: сводные показатели в карточке — производные,
а первоисточник всегда остаётся отдельной записью с датой. Это то, что
позволяет позже пересчитать оценку по другой методике, не потеряв данные.

## Lactation Curve ●

Лактации хранятся массивом внутри животного. Поля одной лактации:

| Поле | Значение |
| --- | --- |
| `number` | номер лактации |
| `calvingDate` | дата отёла |
| `inseminationDate`, `serviceBull` | осеменение внутри лактации |
| `dd` | дойные дни |
| `milkYield` | удой за лактацию |
| `milk305` | удой за 305 дней |
| `fat305`, `protein305` | жир и белок, % |
| `fatKg`, `proteinKg` | жир и белок, кг |
| `scc` | соматические клетки |
| `dryOffDate`, `endDate` | запуск и окончание лактации |

Сейчас удой за 305 дней принимается из импорта. Правильное поведение ◐ —
считать его самим по контрольным дойкам методом ICAR Test Interval Method
и хранить рядом метод расчёта, чтобы значение было воспроизводимо.

Аппроксимация кривой моделями Wood, Wilmink и Ali-Schaeffer ◐ описана
в [standarty.md](standarty.md).

## Журнал правок ●

`animal-revisions` — строка на каждое фактическое изменение осмысленного поля
карточки: путь поля, его название, было, стало, кто и когда. Строки
неизменяемы: журнал, который можно поправить, журналом не является. Удаляются
они только вместе с животным — `animal_id` объявлена `NOT NULL`, и оставленный
журнал не дал бы удалить карточку вовсе.

**Что пишется.** Только поля из явного списка `JOURNALLED`
(`src/lib/animal-journal.ts`): паспорт, происхождение, видимость, выбытие.
Тот же список задаёт, что вообще можно править формами карточки — и это
не экономия, а способ не разойтись: поле, которое можно изменить, но нельзя
записать в историю, — дыра в провенансе.

**Что не пишется.**

| Не попадает в журнал | Почему |
| --- | --- |
| Создание карточки | Правок ещё не было: вся карточка и есть первая версия |
| Загрузка файлом | Её след — пакет данных с исходным файлом и протоколом; построчное дублирование дало бы десятки тысяч строк на один импорт |
| Снимки оценок и экстерьера | Следствие записи в истории, а не правка человека |
| Служебные поля | Ранги сортировки, транслитерация клички, отметки времени |

Отличает их `req.context`, а не наличие пользователя: импорт идёт как раз
от имени приславшего файл. Тот, кто пишет не от лица человека, ставит
`context: { skipJournal: true }` сам.

**Кому видно.** Тем же, кому видна карточка (`animalScopedRead`). Скрывать
правки от того, кому открыты сами данные, значило бы предлагать верить цифрам,
не показывая их происхождения.

## Уровни достоверности данных ●

Шкала из технического задания (Таблица №4, поле `NTRUTH`):

| Уровень | Значение | Смысл |
| --- | --- | --- |
| −1 | Отклонено | ошибки или противоречия, в аналитике не учитывается |
| 0 | Черновик | внесено собственником, не проверено |
| 1 | Проверено собственником | требует внешней верификации |
| 2 | Подтверждено лабораторией | проверены ДНК и продуктивность |
| 3 | Верифицировано ассоциацией | можно выпускать свидетельство |

Правило: племенное свидетельство выпускается с уровня 3, в расчёты индексов
запись попадает с уровня 2. Уровень показан в шапке карточки и виден
на всех вкладках; рядом подсказка с полной шкалой.

Не путать с **достоверностью оценки** (шкала 1…5) — та показывает надёжность
прогноза племенной ценности и стоит рядом с таблицами признаков.

## Пакеты загрузки данных ●

Работа Ассоциации с данными хозяйств построена вокруг пакетов
(`data-submissions`).

Жизненный цикл: `uploaded → checking → checked → accepted` (либо `rejected`).
Каждый переход пишется в историю с указанием, кто и когда его совершил.

Пакет знает, каких животных он касается: импорт CSV записывает затронутые
строки в связь `animals`, а итоги приёмки — в группу `intake`.

| Поле | Что хранит |
| --- | --- |
| `animals` | Записи, созданные или обновлённые этим файлом. Именно им проверка поднимает достоверность |
| `sourceFile` | Сам загруженный файл в `media` — к нему можно вернуться при разборе |
| `intake.rows / created / updated / skipped` | Итоги приёмки четырьмя числами |
| `intake.issues[]` | Непринятые строки: номер строки в файле, индивидуальный номер и причина. До пятидесяти |

Карточка пакета показывает статус, дату и время проверки, комментарий
Ассоциации, статистику «обработано / принято / с ошибками», список записей
пакета, таблицу непринятых строк и протокол ошибок в XLSX. Владелец отмечает
согласие с результатом и нажимает «Опубликовать данные» — пакет переходит
в `accepted`, а уровень достоверности 3 получают записи пакета, а не всё стадо
организации.

**Раздел «История»** в кабинете строится не по пакетам, а по событиям: один
пакет появляется в ленте столько раз, сколько статусов прошёл. Цвет плитки —
состояние шага: оранжевые часы (получен, на проверке), зелёная галочка
(проверен), зелёный флаг (владелец согласовал), красный крест (отклонён).

**Ограничение текущей реализации** ◐: пакет принимается или отклоняется целиком.
Для промышленного объёма нужен построчный приём — часть строк принимается,
часть отклоняется индивидуально с указанием причины.

## Справочники НСИ ●

Справочники живут в базе и редактируются в админке (`/admin`, группа
«Справочники»), а не в коде — требование технического задания.
Минимальный набор полей: код, наименование, описание, порядок сортировки,
признак активности.

Коды сохраняют нумерацию ИАС «Селэкс» (`NPOR`, `NKAT`, `NKKLASS`, `NPV`,
`NRIP`, `NTIP_SPERM`, `NREZOT`, `NMAST`, `NTEXN`), чтобы миграция данных
из «Селэкса» не превратилась в ручное сопоставление тысяч строк.

## Видимость записи ●

`src/lib/visibility.ts`. У видимости два независимых переключателя, и путать
их нельзя:

| Флаг | Что означает |
| --- | --- |
| `publicVisible` | запись вообще присутствует в книге |
| `publicDetails` | карточку можно открыть |

Запись с `publicVisible: true, publicDetails: false` видна в списке (номер,
кличка, владелец, основные показатели), но подробности закрыты. Замок
означает именно решение владельца, а не то, что посетитель не авторизован.

| Кто | Что видит среди животных |
| --- | --- |
| Аноним | записи с `publicVisible = true`; карточка открывается только при `publicDetails = true` |
| Авторизованный | свою организацию полностью плюс чужие записи с `publicVisible = true`; чужая закрытая карточка ему не открывается |
| Администратор Ассоциации | всё |

Раньше замок снимался у любого вошедшего в систему. Это обещало больше, чем
система делала: человек регистрировался и видел ту же закрытую карточку.
Сейчас замок снимают только владелец записи и администратор Ассоциации, а
вошедшему без прав предлагается запросить доступ.

Владелец управляет флагами в разделе «Личный кабинет → Настройки»;
переключатель применяется сразу ко всему стаду.

Для анонимов действует ещё и предел показа: `ANON_SHOW_LIMIT = 36` записей
(три шага по 12). Первые страницы книги открыты всем — это витрина
Ассоциации; дальше предлагается завести учётную запись.

## Запрос доступа к закрытой карточке ●

Коллекция `src/collections/AccessRequests.ts` (`access-requests`). Закрытая
карточка без выхода вредна обеим сторонам: покупатель не может оценить
животное, продавец не узнаёт, что им интересовались. Запрос превращает замок
в начало разговора.

**Цели запроса** (`purpose`): покупка животного или эмбрионов (`purchase`),
приобретение семени быка (`semen`), подбор пар и оценка сочетаемости
(`mating`), проверка происхождения родственных животных (`verification`),
научная работа (`research`), другое (`other`).

**Состояния** (`status`): `new` — ожидает решения хозяйства, `approved` —
доступ открыт, `declined` — отказано.

Хук `beforeChange` при создании берёт заявителя и его организацию из сессии,
а владельца — из самого животного. Ничего из этого нельзя принимать из формы:
иначе запрос можно было бы отправить от чужого имени. При смене статуса тот же
хук проставляет `decidedAt` и `decidedBy` — иначе в журнале осталось бы
«отказано» без даты и без имени.

| Право | Правило | Кто |
| --- | --- | --- |
| Чтение | `accessRequestRead` | заявитель, владелец животного, Ассоциация |
| Изменение | `accessRequestDecide` | только владелец животного (и Ассоциация) |
| Создание | `isAuthenticated` | любой вошедший |
| Удаление | `isAdmin` | Ассоциация |

Ассоциация видит переписку, потому что разбирать спорные случаи приходится ей.
Решение принимает владелец: это его данные.

**Важное ограничение.** Одобрение запроса переключает животное
в `publicVisible / publicDetails = true` — то есть открывает карточку всем
сразу, а не одному заявителю. Точечного доступа «одному хозяйству» в системе
нет: у видимости пока одна степень свободы. Пользовательский интерфейс
предупреждает владельца об этом до нажатия кнопки.

При удалении животного связанные запросы удаляются каскадом — хук
`beforeDelete` у `Animals`. Внешний ключ настроен на `ON DELETE SET NULL`,
а животное в запросе обязательно, поэтому без каскада удаление обрывалось бы
нарушением `NOT NULL`. Осиротевший запрос и сам по себе бессмыслен: он
существует только как разговор о конкретной записи. Тем же хуком уходят
отёлы, дойки, осеменения, случаи болезни, события ленты и значения индекса —
разбор в `docs/refaktoring-bazy.md`, раздел 3.

## Уведомления ●

`src/lib/notifications.ts`. Отдельной таблицы уведомлений нет: она была бы
копией того, что и так лежит в запросах доступа и пакетах загрузки, и рано
или поздно разошлась бы с оригиналом. Лента собирается из самих записей
в момент показа — входящие запросы доступа, ответы на собственные запросы,
изменения по пакетам данных.

Непрочитанное считается по отметке `notifySeenAt` у пользователя: новым
считается всё, что случилось позже неё. Признака «прочитано» у самого события
быть не может — у одного события несколько адресатов, и оно прочитано одним
сотрудником хозяйства и не прочитано другим.

Счётчик для колокольчика в шапке считается отдельным дешёвым запросом
(`countUnreadNotifications`): шапка рисуется на каждой странице, и тянуть ради
цифры всю ленту с раскрытыми связями было бы расточительно.

Настройки рассылки — поля пользователя `notifySubmissions` (о пакетах данных),
`notifyTrust` (об изменении уровня достоверности), `notifyNews` (новости
Ассоциации).

## Архив ●

Признак `archived` у животного и константа `NOT_ARCHIVED` в
`src/lib/animal-query.ts`. Условие подмешивается в каждый отбор списка
(`buildAnimalWhere`) и в счётчики главной страницы и личного кабинета —
счётчики строятся прямыми запросами, поэтому константа вынесена отдельно.

В архиве лежат не выбывшие животные, а служебные записи предков: они заведены
ради построения родословных и в стаде никогда не стояли. ТЗ запрещает удалять
данные, поэтому такие записи остаются в системе и открываются по ссылке
из родословной, но в книгу и в «Мои животные» не попадают — иначе они
смешиваются с настоящим поголовьем и ломают счётчики.

Условие записано через `or` (`archived = false` либо поля нет вовсе):
у записей, заведённых до появления признака, в поле NULL, и `not_equals: true`
отбросил бы и их тоже.

Оговорка: фильтр применяется только на серверных страницах приложения.
Через REST и GraphQL архивные записи по-прежнему возвращаются — запрос к
`/api/animals` без явного условия отдаёт их наравне с остальными.

## Целостность на уровне базы ●

Правила предметной области продублированы в самой схеме — 28 CHECK-ограничений
(`src/lib/db-constraints.ts`, подключаются через `afterSchemaInit` адаптера).
Проверки в хуках Payload работают, только пока запись идёт через Payload;
скрипт переноса, ручной `UPDATE` и будущий конвейер BLUP ходят мимо.

В базе: животное не может быть своим родителем и отец не может быть матерью;
уровни достоверности в своих шкалах (данные −1…3, оценка 1…5); проценты крови,
инбридинга, жира и белка в допустимых пределах; номера отёлов, лактаций
и попыток осеменения строго положительны; σ в базе сравнения не ноль.

В приложении остаётся то, для чего нужна другая строка таблицы: пол родителей,
порядок дат рождения, отсутствие циклов в родословной. `CHECK` видит одну
строку и только неизменяемые выражения — граница проходит по этому.

Восемь счётчиков переведены из `numeric` в `integer`: номер отёла и лактации,
попытка осеменения, число доз, уровень достоверности, объём выборки в базе
сравнения. Границы диапазонов берутся из полей коллекций (`min` / `max`), а не из текста
требований: расхождение между тем, что разрешает форма, и тем, что разрешает
база, — отложенная авария. Перед применением такой миграции запускается
`npm run db:precheck` — он прогоняет те же правила как SELECT по целевой базе
и показывает строки, которые не пройдут. Полный разбор —
`docs/refaktoring-bazy.md`.

## Импорт и экспорт ●

- **Импорт** — отдельная страница `/account/import` («Личный кабинет →
  Мои животные → Загрузить данные»), CSV с разделителем `;` или `,`
  (определяется по первой строке), файл до 8 МБ. Распознаются колонки:
  `Инд.№`, `Кличка`, `Пол`, `Дата рождения`, `Возраст`, `Состояние`,
  `Удой, л`, `Жир, %`, `Белок, %`, `Жир, кг`, `Белок, кг`, `ИПЦ`.
  Колонки `Возраст` и `Состояние` заголовок распознаёт (`ageGroup`, `state`),
  но в сохраняемый объект они не попадают — значения этих полей
  из файла сейчас теряются. Существующие животные обновляются по `Инд.№`,
  чужие записи пропускаются.
- **Экспорт** — `GET /account/export?format=csv|json`, только животные
  своей организации, не более 5000 записей за раз.
