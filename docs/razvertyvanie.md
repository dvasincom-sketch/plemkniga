## Локальный запуск

Нужен Node не ниже **22.12** — версия зафиксирована в поле `engines`
файла package.json и в базовых образах Dockerfile (`node:22.12-alpine`),
чтобы локальная сборка и сборка в контейнере совпадали.

```bash
cp .env.example .env          # DATABASE_URI и PAYLOAD_SECRET
npm install
npm run generate:types        # типы Payload → src/payload-types.ts
npm run seed                  # демо-данные
npm run dev
```

> `npm run seed` **очищает** перед наполнением: documents, events,
> health-events, milk-tests, inseminations, calvings, data-submissions,
> access-requests, media, animals, herds, technicians, users, organizations
> и все справочники.
>
> Если менялась структура коллекций, пересоздайте базу перед сидом —
> Payload не всегда может изменить тип уже существующей колонки:
> `dropdb plemkniga && createdb plemkniga`

### Предохранитель сида

Если в базе уже есть животные, `npm run seed` останавливается с кодом 1
и требует переменную `SEED_CONFIRM=1`:

```bash
SEED_CONFIRM=1 npm run seed
```

Причина в том, что сид начинается с полной очистки: это наполнение пустой
базы, а не обновление данных. Однажды его запуск уничтожил данные на проде.
В сообщении об остановке скрипт печатает замаскированную строку подключения —
перепутать локальную базу с прод-базой проще, чем кажется. Реализация —
`src/seed/index.ts`.

Чтобы достроить родословную, не удаляя ничего, сид не нужен: для этого есть
`npm run pedigree:deep`.

Демо-доступы после сида — восемь учётных записей, пароль у всех
`plemkniga123`:

| Роль | Логин |
| --- | --- |
| Фермер (ЗАО «Назаровское») | `farmer@nazarovskoe.ru` |
| Администратор Ассоциации | `admin@holstein-russia.ru` |

## Полезные команды

```bash
npm run dev                 # разработка
npm run build && npm start  # прод-сборка
npm run generate:types      # перегенерировать типы после правки коллекций
npm run generate:importmap  # после добавления кастомных компонентов в админку
npm run lint                # next lint
npm run payload migrate:create
npm run payload migrate

npm run backfill:sort-ranks  # пересчитать служебные ранги сортировки
npm run repair:uuid          # починить animals.uuid, если push падает на уникальном индексе

npm run pedigree:deep -- <инд-номер> [глубина]  # достроить родословную вглубь
```

`pedigree:deep` только добавляет записи предков и связи — он ничего
не удаляет и не перезаписывает, поэтому его можно запускать против
работающей системы, в отличие от сида.

### Если Payload не стартует из-за уникального индекса

```
could not create unique index "animals_uuid_idx"
detail: Key (uuid)=(Голштинская) is duplicated.
```

При изменении структуры коллекции drizzle push иногда принимает появление новой
колонки за переименование старой и переносит в неё чужие значения — так в `uuid`
попадают, например, названия пород. Дальше не стартует ничего: ни `npm run dev`,
ни другие скрипты, потому что все они поднимают Payload.

`npm run repair:uuid` работает напрямую через драйвер, в обход Payload:
заменяет значения, не похожие на UUID, и дубликаты на свежие UUID.
Остальные поля не трогает. После него `npm run dev` проходит.

Если данные демонстрационные, быстрее пересоздать базу:
`dropdb plemkniga && createdb plemkniga && npm run seed`.

## Запуск в Docker

```bash
cp .env.example .env
nano .env      # заменить значение существующей строки PAYLOAD_SECRET
docker compose up -d --build
```

`PAYLOAD_SECRET` уже есть в `.env.example`, поэтому дописывать строку в конец
файла (`echo … >> .env`) не нужно: получится две строки с одним именем,
и какая из них победит, зависит от того, кто читает файл. Значение
генерируется командой `openssl rand -base64 32`.

Приложение — на `http://localhost:3000`, база — во внутренней сети Compose
(наружу порт не публикуется). Внешний порт задаётся переменной `APP_PORT`.
Медиафайлы и данные БД лежат в томах `media` и `pgdata`.

### Почему в контейнере запускается `node server.js`, а не `npm start`

В `next.config.mjs` включён `output: 'standalone'`: сборка складывает
в `.next/standalone` самодостаточный сервер вместе с нужным подмножеством
`node_modules`. Dockerfile копирует именно этот каталог, поэтому в образе
нет ни полного `node_modules`, ни скриптов package.json — `npm start`
там запускать нечем. Размер образа за счёт этого меньше в разы.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URI` | строка подключения к PostgreSQL |
| `PAYLOAD_SECRET` | ключ подписи токенов, `openssl rand -base64 32` |
| `NEXT_PUBLIC_SERVER_URL` | публичный адрес приложения |
| `PAYLOAD_DB_PUSH` | **только для разработки**: правит схему на лету. Семантика инверсная — push включён по умолчанию, выключает его единственное значение `false` (`push: process.env.PAYLOAD_DB_PUSH !== 'false'`). Значение `true` ни на что не влияет. На проде не действует в любом случае — см. раздел о миграциях |
| `PORT` | порт приложения, по умолчанию 3000. В образе задан жёстко (`ENV PORT=3000`), менять его через `.env` бесполезно |
| `APP_PORT` | порт, на котором docker compose публикует приложение наружу, по умолчанию 3000. Именно его и меняют, когда 3000 занят |
| `MEDIA_DIR` | каталог для медиафайлов; в образе `/app/media`, туда же смонтирован том `media`. Без него файлы легли бы в слой контейнера и пропали при пересоздании |
| `SEED_CONFIRM` | `1` разрешает `npm run seed` работать против непустой базы |
| `DATABASE_SSL` | принудительно включить TLS, если его нет в строке подключения |
| `DATABASE_CA_CERT` | CA-сертификат базы: PEM целиком или в base64. Нужен, только если хотите проверку подлинности сервера |
| `DATABASE_SSL_REJECT_UNAUTHORIZED` | явно включить (`true`) или выключить (`false`) проверку сертификата, независимо от `sslmode` |

В `.env.example` есть ещё `SEED_ENABLED`. Она не читается нигде в коде —
это остаток от ранней версии, на поведение не влияет.

### Почему `sslmode` вырезается из строки подключения

Ловушка, которая стоила нескольких деплоев. У node-postgres два решения,
которые вместе дают неожиданный результат:

1. Увидев `sslmode` в строке подключения, драйвер **игнорирует** переданный
   отдельно объект настроек TLS и берёт настройки только из строки.
2. `sslmode=require` он трактует как `verify-full` — включает полную проверку
   сертификата, хотя в PostgreSQL этот режим означает «шифруй, но не проверяй».

В итоге строка подключения, с которой без вопросов работают psql и другие
проекты, здесь падала с `self-signed certificate in certificate chain`,
и никакие переменные окружения на это не влияли — их просто не читали.
Причём в логах всё выглядело правильно: приложение сообщало «шифрование
без проверки сертификата», а драйвер в это время проверял.

Поэтому приложение отдаёт драйверу строку **без `sslmode`**, а режим TLS
задаёт отдельным объектом. Обе строки видны в `/healthz`:
`connectionString` — как задали вы, `connectionStringForDriver` — как ушла
в драйвер. Во второй `sslmode` быть не должно.

### Режим TLS определяется по `sslmode`, как в libpq

Тонкость, на которой легко потерять вечер: **`sslmode=require` означает
«шифруй, но сертификат не проверяй»**. Проверку включают только `verify-ca`
и `verify-full`. Драйвер node-postgres таких правил не знает и проверяет
всегда, когда ему передали настройки TLS, — поэтому строка подключения,
с которой без вопросов работают psql и другие клиенты, здесь падала
с `self-signed certificate in certificate chain`.

Теперь поведение совпадает с общепринятым:

| В строке подключения | Что делает приложение |
| --- | --- |
| `sslmode=require` | шифрует, сертификат не проверяет — CA не нужен |
| `sslmode=verify-ca` или `verify-full` | проверяет; для самоподписанного сертификата задайте `DATABASE_CA_CERT` |
| `sslmode=prefer`, `allow`, `disable` | TLS выключен |
| `sslmode` не задан | TLS выключен |
| `sslmode` не задан, но `DATABASE_SSL=true` | шифрует; проверка включается только `DATABASE_CA_CERT` или `DATABASE_SSL_REJECT_UNAUTHORIZED=true` |

Текущий режим виден в логе при старте и в поле `tls` ответа `/healthz`.

### Как приложение ищет строку подключения

Разные платформы называют переменную по-разному, поэтому строка подключения
ищется по очереди под именами `DATABASE_URI`, `DATABASE_URL`, `POSTGRES_URI`,
`POSTGRES_URL`, `POSTGRESQL_URL`, `PG_URI`, `PG_URL`, `DB_URI`, `DB_URL`.
Если ни одного нет — собирается из отдельных `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (принимаются также варианты
с префиксами `PG`, `DB_` и `DATABASE_`: `DATABASE_HOST`, `DATABASE_PORT`,
`DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME`).

Сборка из частей срабатывает, только если заданы одновременно хост,
пользователь и имя базы. Пароль и порт необязательны: без порта берётся 5432.
Половина настроек строку не даст — иначе приложение молча уходило бы
на localhost вместо того, чтобы сообщить, что подключаться некуда.

Откуда взято значение, видно в логе при старте и в ответе `/healthz`
(поле `takenFrom`). Реализация — `src/lib/db-url.ts`.

## Схема базы: push в разработке, миграции на проде

Это неочевидно и стоило одного неудачного деплоя, поэтому подробно.

В разработке Payload сравнивает схему с конфигом и правит базу на лету
(`drizzle push`). На проде он этого **не делает** — в исходниках адаптера прямо
записано «Only push schema if not in production». То есть `PAYLOAD_DB_PUSH=true`
в переменных окружения прод-приложения ни на что не влияет: таблицы сами
не появятся, и первый же запрос упадёт с `relation "animals" does not exist`.

Схему на проде создают миграции из `src/migrations`. Они переданы адаптеру
через `prodMigrations`, поэтому Payload прогоняет их **сам при старте**:
применяются только те, которых ещё нет в таблице `payload_migrations`,
так что повторный запуск безопасен и отдельного шага в деплое не нужно.

### Что уже есть в `src/migrations`

| Миграция | Что делает |
| --- | --- |
| `20260814_195548` | базовая схема: все перечисления, таблицы коллекций, индексы и связи |
| `20260815_061539` | `animals.for_sale` и индекс по этой колонке |
| `20260815_075706` | `users.notify_submissions`, `users.notify_trust`, `users.notify_news` |
| `20260815_112204_access_requests` | таблица `access_requests`, два перечисления под неё и `users.notify_seen_at` |

Порядок и состав списка задаёт `src/migrations/index.ts` — именно он передаётся
адаптеру, а не содержимое каталога.

### После изменения структуры коллекций

```bash
npm run payload migrate:create -- --name опишите-изменение
git add src/migrations && git commit -m "Миграция: …"
```

Файл миграции обязательно коммитится: без него прод не узнает о новых полях.
Проверить миграцию на чистой базе перед пушем:

```bash
createdb plemkniga_check
DATABASE_URI=postgres://…/plemkniga_check npm run payload migrate
```

## Деплой на Timeweb Cloud

### 1. Приложение из Git (рекомендуется)

1. Запушьте репозиторий в GitHub или GitLab.
2. Timeweb Cloud → **Приложения** → *Создать* → тип **Docker**, укажите
   репозиторий и ветку. Dockerfile в корне подхватится автоматически.
3. Timeweb Cloud → **Базы данных** → создайте **PostgreSQL 16**. Скопируйте
   строку подключения; для внешнего подключения добавьте `?sslmode=verify-full`
   (или `?sslmode=require`, если сертификат не устанавливаете).
4. Задайте переменные окружения приложения — именно **переменные окружения
   контейнера**, а не аргументы сборки. Аргумент сборки в рантайме не виден,
   и приложение не найдёт базу.
5. Первый деплой создаст схему миграциями автоматически — они прогоняются
   при старте приложения. `PAYLOAD_DB_PUSH` на проде задавать не нужно.
6. Домен и бесплатный TLS — в разделе «Домены» приложения.

### 2. Облачный сервер и docker compose

```bash
ssh root@<ip>
git clone <repo> /opt/plemkniga && cd /opt/plemkniga
cp .env.example .env && nano .env       # PAYLOAD_SECRET, NEXT_PUBLIC_SERVER_URL
docker compose up -d --build
```

Дальше — nginx или Caddy как reverse-proxy на порт 3000 и сертификат
Let's Encrypt.

## Две пробы состояния

| Эндпоинт | Что проверяет | Кто использует |
| --- | --- | --- |
| `/healthz/live` | жив ли процесс Node, к базе не обращается — всегда 200 | `HEALTHCHECK` в Dockerfile |
| `/healthz` | связь с базой, переменные окружения, подсказки — всегда 200, состояние в поле `status` | человек при диагностике |

Разделение намеренное. Если healthcheck ходит на `/healthz`, то незаданная
строка подключения делает контейнер unhealthy, и платформа помечает деплой
как неуспешный, не дав посмотреть причину. Теперь контейнер поднимается
в любом случае, а причина видна на `/healthz`.

`/healthz` отвечает кодом 200 даже при недоступной базе — намеренно: многие
браузеры и утилиты на 5xx не показывают тело ответа, и диагностика становится
невидимой. Состояние передаётся полем `status`: `ok` или `error`.

### У разделения есть цена, и её надо знать

**«Деплой прошёл успешно» не значит, что сайт работает.** `HEALTHCHECK` ходит
на `/healthz/live`, а тот к базе не обращается вовсе — и отвечает `200`
контейнеру, который не может сделать ни одной страницы. Это плата за то, чтобы
причина была видна; но читать «Deploy succeeded» как «всё хорошо» нельзя.
После деплоя смотреть надо на `/healthz`, а не на строку в панели.

**`/healthz` не должен уметь зависать.** Однажды сумел: база перестала
отвечать (не отказала — замолчала), у пула не было срока на соединение, проба
ждала вместе со всеми и не отдавала ничего. Инструмент, которым узнают
причину, оказался недоступен ровно тогда, когда понадобился. Теперь срок есть
в двух местах: `connectionTimeoutMillis` у пула (5 с, переопределяется
`DATABASE_CONNECT_TIMEOUT_MS`) и собственный срок пробы (8 с). Разбор —
решение №39.

**`uptimeSec` у `/healthz/live` — это диагностика, а не украшение.** Значение
меньше времени, прошедшего с деплоя, означает, что контейнер перезапускался.

## Диагностика

Если главная отдаёт «Произошла ошибка на сервере», откройте
`https://<домен>/healthz`. Ответ содержит:

- состояние подключения к базе и текст ошибки;
- блок `env` с полями `connectionString` (строка как её задали, пароль
  замаскирован), `connectionStringForDriver` (что реально ушло в драйвер),
  `takenFrom` (под каким именем найдена строка), `tls`, `caCertificate`,
  `payloadSecret`, `serverUrl`, `dbPush`, `nodeEnv`;
- блок `visibleEnv` — **все** переменные окружения, похожие на настройки базы,
  с замаскированными паролями. По нему сразу видно, что платформа реально
  передала в контейнер;
- список подсказок `hints` под конкретную ошибку;
- `tookMs` — сколько заняла проверка.

Ключи ответа латиницей намеренно: панели и консоли иногда угадывают кодировку
неверно, и русские имена полей превращаются в мусор ровно там, где нужна
ясность. У `/healthz/live` полей три: `status`, `service` и `uptimeSec`.

Экран ошибки показывает `digest` — по нему запись находится в логах приложения.

| Симптом | Что делать |
| --- | --- |
| `connectionString: НЕ НАЙДЕНА` | проверить `visibleEnv`; убедиться, что переменная задана как переменная окружения контейнера, а не аргумент сборки, и что после сохранения запущен новый деплой |
| `ECONNREFUSED 127.0.0.1:5432` | строка подключения до драйвера не дошла — это всегда проблема переменной окружения, а не сети |
| `no pg_hba.conf entry ... SSL off` | добавить `?sslmode=require` в конец строки подключения |
| `self-signed certificate in certificate chain` | проверьте `sslmode` в строке подключения: с `require` проверки быть не должно. Если нужен `verify-full` — задайте `DATABASE_CA_CERT` |
| `could not create unique index … is duplicated` | в таблице дубликаты в поле с уникальным индексом; для `animals.uuid` — `npm run repair:uuid` |
| `database ... does not exist` | создать базу в панели или указать существующую |
| `relation ... does not exist` | схемы в базе нет. Применить миграции: `npm run payload migrate` против прод-строки подключения — либо дождаться деплоя, контейнер прогоняет `prodMigrations` при старте. `PAYLOAD_DB_PUSH` здесь не поможет: на проде `NODE_ENV=production`, и push Payload отключает сам |
| `ENOTFOUND` / `EAI_AGAIN` | хост базы не резолвится из контейнера — проверить адрес и сетевые правила |
| `ETIMEDOUT` / «база не ответила за 8000 мс» | база **молчит**, а не отказывает: пакеты до неё не доходят. Почти всегда это список доверенных IP базы или файрвол — адреса контейнера в списке нет либо он сменился при перезапуске. Проверка: `nc -vz <хост> 5432` с любой машины. «succeeded» — база жива и пускает эту машину, значит дело в адресе контейнера; висит без ответа — закрыто для всех. Надёжное лечение, если приложение и база у одного провайдера, — строка подключения по внутреннему адресу |
| Страница висит, `/healthz` не отвечает, `/healthz/live` отвечает | процесс жив, база молчит, а срока на соединение нет. Так было до решения №39; если повторилось — проверить, что `connectionTimeoutMillis` не потерялся при правке `payload.config.ts` |
| В логе `⨯ uncaughtException: Error: read ETIMEDOUT` и частые перезапуски | оборвалось простаивающее соединение пула. Само по себе процесс убивать не должно (`guardPool` в `src/lib/payload.ts`); если убивает — слушатель не навесился, потому что `getClient()` обошли и вызвали `getPayload` напрямую |

Различать отказ и тишину важнее, чем кажется. `ECONNREFUSED` означает, что
до сервера дошли и он ответил «нельзя»: порт закрыт, служба не поднята.
`ETIMEDOUT` означает, что ответа не было вовсе. Файрвол и список доверенных
IP не отказывают — они выбрасывают пакеты. Поэтому «с моей машины порт
открыт» ничего не опровергает: вопрос всегда в том, пускают ли **контейнер**.

После успешного деплоя зайдите на `/admin` — Payload предложит создать
первого пользователя-администратора.

## Хранение медиа

Каталог медиа вынесен в переменную `MEDIA_DIR` (`src/collections/Media.ts`,
в образе — `/app/media`), поэтому в docker compose он монтируется томом
и переживает пересоздание контейнера.

Этого достаточно для одного сервера, но локальный диск контейнера в облаке
эфемерен, а при нескольких экземплярах приложения файлы окажутся у каждого
свои. Следующий шаг — S3 Timeweb Cloud: плагин хранилища подключается рядом,
править `staticDir` в коде для этого не нужно.

```bash
npm i @payloadcms/storage-s3
```

```ts
// payload.config.ts
import { s3Storage } from '@payloadcms/storage-s3'

plugins: [
  s3Storage({
    collections: { media: true },
    bucket: process.env.S3_BUCKET!,
    config: {
      endpoint: 'https://s3.twcstorage.ru',
      region: 'ru-1',
      forcePathStyle: true,
      credentials: {
        accessKeyId: process.env.S3_ACCESS_KEY!,
        secretAccessKey: process.env.S3_SECRET_KEY!,
      },
    },
  }),
]
```

## Интерфейсные решения

- **Каталог книги** — условия отбора стоят слева от результатов и прилипают
  при прокрутке, поэтому пользователь меняет условие и сразу видит выдачу.
  Над таблицей — счётчик найденного, переключатель сортировки и «фишки»
  активных условий с крестиком: видно, почему выдача такая, и любое условие
  снимается одним кликом. Заставка показывается только на чистой книге —
  между условиями и результатами не должно стоять ничего декоративного.
  На узком экране колонка условий сворачивается, а таблица заменяется
  карточками.
- **Приоритет колонок таблицы** — основные колонки видны всегда,
  вспомогательные появляются, когда для них есть место. Горизонтальный скролл
  по четырнадцати колонкам не даёт сравнивать животных.
- **Липкий футер** — `body` растянут на `100dvh` флекс-колонкой, `main`
  забирает свободное место, поэтому подвал прижат к низу даже на коротких
  страницах.
- **Свои выпадающие списки** — `src/components/Select.tsx` вместо нативного
  `<select>`: роль `listbox`, управление стрелками, Home/End, поиск по первым
  буквам, Esc и клик вне списка закрывают его. Значение уходит в форму скрытым
  input, поэтому компонент работает и в GET-поиске, и в server actions.
- **Подсказки** — `src/components/InfoTip.tsx` рисуется порталом в `body`
  с координатами от кнопки и зажимается в границы окна, поэтому не обрезается
  ни родительским `overflow`, ни краем экрана.
- **Шапка** — один вход в кабинет (имя пользователя с аватаром) и одна кнопка
  выхода.
- **Шрифты** — Onest для интерфейса, Unbounded для крупных числовых показателей
  (класс `.stat-value`). Оба подключены из npm, без обращений к внешним CDN.
- **Без фотографий** — вместо фотозаглушек используются числовые сводки,
  типографические плашки и монограммы: обобщённое фото животного ничего
  не сообщает о конкретной записи.
