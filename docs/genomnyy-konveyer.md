# Геномный конвейер

Архитектура обработки данных генотипирования: от файла с чипа до племенной
оценки. Документ описывает целевое решение и честно отмечает, что из него
реализовано.

Статусы: ● работает · ◐ спроектировано · ○ план.
**Сводно: в коде сейчас нет ничего из этого документа.** Реализована только
форма хранения результата оценки — пара «прогноз + достоверность R,%»
у каждого признака животного. Сами значения приходят извне.

---

## Общая схема

```
файл с чипа                                                 
PED/MAP · VCF · FinalReport
      │
      ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ 1. Приём     │──▶│ 2. Контроль  │──▶│ 3. Импутация │
│ нормализация │   │ качества QC  │   │ до общей     │
│ аллелей и    │   │ call rate    │   │ панели       │
│ координат    │   │ MAF · HWE    │   │              │
└──────────────┘   └──────┬───────┘   └──────┬───────┘
                          │                  │
                   протокол QC               ▼
                   (что отбраковано   ┌──────────────┐
                    и почему)         │ 4. Матрицы   │
                                      │ родства A и G│
                                      └──────┬───────┘
                                             ▼
                                      ┌──────────────┐
                                      │ 5. ssGBLUP   │
                                      │ H = A + G    │
                                      └──────┬───────┘
                                             ▼
                                     gEBV → индексы →
                                     подбор пар
```

## Ступень 1. Приём и нормализация ◐

### Форматы на входе

| Формат | Состав | Особенности |
| --- | --- | --- |
| **PLINK PED/MAP** | `.ped` — 6 служебных колонок (Family ID, Individual ID, Paternal ID, Maternal ID, пол 1/2, фенотип) и далее пары аллелей; `.map` — хромосома, ID маркера, генетическая дистанция, позиция в парах оснований | текстовый, читаемый, объёмный |
| **PLINK бинарный** | `.bed` — генотипы, `.fam` — первые 6 колонок PED, `.bim` — MAP плюс две колонки имён аллелей | компактный, стандарт для расчётов |
| **VCF** | текущая опубликованная спецификация — VCFv4.5 | универсален, но избыточен для чипов |
| **Illumina FinalReport** | «длинный» формат: строка на пару SNP × образец, минимум SNP Name, Sample ID, Allele1, Allele2, обычно плюс GC Score, X/Y, B Allele Freq, LogR. Есть и матричный вариант: строки — животные, столбцы — SNP | приходит прямо из GenomeStudio |

### Подводный камень первый: три схемы кодирования аллелей

Это главный источник тихих ошибок при объединении данных с разных чипов
и из разных лабораторий. Схем три, и они не взаимозаменяемы:

- **TOP/BOT** — проприетарная схема Illumina. Определяется по самому SNP
  и окружающей последовательности, без обращения к внешним базам.
  A/B назначаются по TOP/BOT и **не совпадают** с REF/ALT из VCF.
- **Plus/Minus** — ориентация относительно сборки генома. Меняется между
  версиями сборки; в манифесте чипа за это отвечает колонка RefStrand.
- **Forward/Reverse** — относительно записи RefSNP в dbSNP, и это не то же
  самое, что FWD/REV самой dbSNP.

Практическое следствие: `[T/C]` на цепи BOT — это `[A/G]` на TOP. Если слить
два набора без приведения к одной конвенции, часть генотипов окажется
инвертирована, и ошибка не проявится как сбой — она проявится как ухудшение
точности оценки, причину которого потом будут искать месяцами.

**Решение в архитектуре:** нормализация — обязательный, а не опциональный шаг
приёма. Исходный файл хранится неизменным, нормализованная версия — отдельно,
конвенция фиксируется в метаданных загрузки.

### Подводный камень второй: сборка генома

Текущая референсная сборка Bos taurus — **ARS-UCD2.0**
(RefSeq GCF_002263795.3). При этом большинство манифестов чипов и публикаций
до сих пор в координатах **ARS-UCD1.2**, а более старые наборы могут быть
в UMD3.1 или Btau_4.x.

Сравнивать маркеры по паре «хромосома + позиция» между наборами в разных
сборках нельзя — получатся ложные совпадения. Нужен либо liftover,
либо сопоставление по идентификатору маркера. Сборка обязана храниться
в метаданных каждой загрузки как обязательное поле.

### Что храним в модели данных

| Поле | Назначение |
| --- | --- |
| `animal` | связь с карточкой животного |
| `chip` | модель чипа и число маркеров |
| `assembly` | сборка генома координат (`ARS-UCD1.2` / `ARS-UCD2.0` / …) |
| `alleleCoding` | конвенция кодирования исходника (`TOP` / `PLUS` / `FORWARD`) |
| `callRate` | доля успешно прочитанных маркеров по образцу |
| `laboratory` | кто выполнил генотипирование |
| `sourceFile` | исходный файл без изменений — для повторной обработки |
| `qcStatus` | принят / отбракован, с причиной |

## Ступень 2. Контроль качества ◐

### Пороги

Академическая практика на бычьих массивах:

| Проверка | Порог отбраковки |
| --- | --- |
| Call rate маркера | < 0,90 |
| MAF маркера | < 0,01 |
| Пропуски по образцу | > 10% |

Производственная практика CDCB (США) — она интереснее, потому что описывает
не только отбраковку записей, но и **оценку самой лаборатории**:

- генотип животного с call rate < 90% не попадает в национальную базу;
- лаборатория считается не прошедшей контроль, если доля SNP с call rate
  ниже 90% превышает 0,5% для платформы Illumina или 2% для Affymetrix;
- порог менделевских конфликтов «родитель–потомок» — 0,05% (5 на 10 000);
- отдельная проверка по Харди–Вайнбергу применяется к сабмишенам от 50 генотипов.

Для сравнения масштаба: в геномной оценке США используется отобранный набор
из 78 964 SNP и подмножество 3 552 SNP для быстрых сверок.

**Продуктовое следствие.** Оценка лаборатории — это функция, которую стоит
сделать явной. Ассоциация, принимающая генотипы от нескольких лабораторий,
должна видеть их сравнительное качество, а не только результат по каждому
животному. Это её прямой инструмент влияния.

### Протокол QC

Отбраковка без объяснения вызывает недоверие. Каждая загрузка должна
завершаться протоколом: сколько образцов и маркеров принято, сколько
отбраковано и по какому критерию, какие менделевские конфликты обнаружены.
Механика уже есть в системе — так работают пакеты загрузки фенотипа
(`data-submissions` с протоколом ошибок в XLSX), и генотипы логично
встроить в тот же цикл.

## Ступень 3. Импутация ○

Хозяйства генотипируют разными чипами: дешёвыми низкой плотности для товарного
стада, плотными — для быков и племенного ядра. Порядок величин:

| Чип | Маркеров |
| --- | --- |
| EuroGenomics EuroG MD | ~60 000 |
| Illumina BovineSNP50 v3 | 53 218 |
| GGP Bovine 150K | свыше 134 000 |
| Thermo Fisher Axiom Bovine BOS 1 | свыше 640 000 |
| Illumina BovineHD | 777 962 |

Чтобы оценивать всех вместе, генотипы приводят к общей панели — достраивают
недостающие маркеры по неравновесию по сцеплению и родственным связям.

Инструменты, применяемые в молочном скотоводстве:

- **FImpute** — использует информацию о родственниках, базовый выбор в породном
  контексте с глубокими родословными;
- **Beagle** — популяционная импутация и пре-фазирование референс-панелей;
- **Minimac** — импутация по подготовленной референс-панели.

Две ступени глубины: импутация «до HD» — с 50K на плотность порядка 777K,
и импутация «до WGS» — далее на полногеномные варианты по референс-панели
секвенированных животных (проект 1000 Bull Genomes).

**Ограничение, о котором надо говорить прямо.** Точность импутации зависит
от размера и породного состава референс-панели. Для российской голштинской
популяции такой панели нет — её нужно накапливать. Это не программистская
задача и не решается кодом: это годы сбора генотипов. Реалистичный путь —
начинать с импутации по международным панелям с явным контролем точности.

## Ступень 4. Матрицы родства ○

**A — матрица родства по родословной.** Строится рекурсивно из связей
отец/мать; для BLUP нужна не сама A, а её обратная A⁻¹, которая по методу
Хендерсона считается напрямую по родословной без обращения матрицы.
Диагональный элемент a_ii = 1 + F_i, где F_i — коэффициент инбридинга
животного, тот самый, который уже считается в системе по формуле Райта.

**G — геномная матрица родства.** Строится по центрированным генотипам
(классическая параметризация VanRaden):

```
G = Z Z' / (2 Σ pᵢ(1 − pᵢ))
```

где Z — матрица генотипов, центрированная по частотам аллелей p, а знаменатель
приводит G к масштабу A.

**Согласование.** A и G должны быть в одной шкале, иначе объединение даст
смещённые оценки. Стандартный приём — линейная корректировка G по средним
значениям блока A22 (подматрица A для генотипированных животных),
плюс регуляризация вида G* = (1 − w)·G + w·A22 для обратимости.

## Ступень 5. Single-Step GBLUP ○

Классический BLUP использует только родословную, геномный GBLUP — только
генотипированных животных. Single-step объединяет то и другое в одну матрицу H,
чтобы генотипированные и негенотипированные животные оценивались совместно
в одной системе уравнений:

```
             ⎡ 0            0        ⎤
H⁻¹ = A⁻¹ +  ⎢                       ⎥
             ⎣ 0     G⁻¹ − A₂₂⁻¹     ⎦
```

где A₂₂ — блок A для генотипированных животных. Дальше — обычные уравнения
смешанной модели, где вместо A⁻¹ подставляется H⁻¹.

Почему именно single-step для этого проекта: в племенной книге всегда будет
большинство животных без генотипа — товарное поголовье генотипируют выборочно.
Раздельная оценка означала бы два несопоставимых рейтинга в одной системе,
что для пользователя выглядит как ошибка.

**Что нужно, кроме кода:**

- референс-популяция с одновременно известными генотипом и фенотипом
  достаточного размера — это главный ограничитель, и он не программистский;
- оценки компонент дисперсии для признаков, желательно на российской популяции;
- вычислительные мощности: обращение G для десятков тысяч генотипированных
  животных — тяжёлая операция, для больших популяций применяют APY-аппроксимацию.

**Реалистичная последовательность:** сначала BLUP по родословной на накопленном
фенотипе — он даёт работающий продукт и проверяет всю цепочку сбора данных.
Только когда накоплена референс-популяция, имеет смысл переходить к ssGBLUP.
Обратный порядок — частая и дорогая ошибка.

## Что из этого попадает в модуль подбора пар

Геномный конвейер нужен не сам по себе. Два его выхода питают продуктовые
функции напрямую:

1. **gEBV по признакам** → пользовательский индекс → ранжирование быков
   и коров под экономику конкретного хозяйства.
2. **Геномный инбридинг F_ROH и статусы летальных гаплотипов** →
   ограничения в задаче подбора пар.

```
F_ROH = (суммарная длина ROH) / (длина покрытого аутосомного генома)
```

ROH — протяжённые участки гомозиготности; их суммарная доля измеряет
фактическую гомозиготность генома, тогда как формула Райта даёт лишь
ожидаемую при полной и достоверной родословной.
