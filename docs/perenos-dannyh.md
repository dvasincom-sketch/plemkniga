# Перенос демонстрационных данных на прод

Два способа. Первый проще и почти всегда достаточен.

---

## Способ 1. Запустить сид против прод-базы (рекомендую)

### Сначала — миграции

Сид запускается локальным кодом против удалённой базы. Код знает про все поля
последнего коммита, база — только про те, что создали применённые миграции.
Если между ними разрыв, сид падает ещё на очистке:

```
error: column animals.for_sale does not exist
```

Это не поломка сида: на проде просто нет колонки, которую добавила миграция,
до неё не дошедшая. `PAYLOAD_DB_PUSH=false` (и правильно) не даёт скрипту
дописать колонку самому.

Миграции на прод попадают двумя путями — сами при старте контейнера после
деплоя (`prodMigrations` в конфиге) или вручную, не дожидаясь деплоя:

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
npm run payload migrate
```

Команда идемпотентна: применённые миграции пропускаются, применяются только
новые. Порядок для нового кода всегда один — `git push` → деплой (или
`payload migrate` вручную) → сид.

### Если `payload migrate` падает на первой миграции

```
error: type "enum_users_role" already exists
```

и следом простыня SQL на несколько экранов. Выглядит как поломка миграции —
на деле это расхождение базы и журнала, и данные при этом целы.

Причина. В режиме разработки Payload держит схему в актуальном виде сам,
командой `drizzle push`, минуя миграции. Таблицы появляются, записей
в `payload_migrations` не остаётся. Потом на такой базе запускают
`payload migrate`, она честно берёт первую миграцию — и PostgreSQL отвечает,
что тип уже есть.

Чинится сверкой журнала с фактическим состоянием базы:

```bash
npm run migrate:baseline            # показать расхождения, ничего не меняя
npm run migrate:baseline -- --apply # отметить применённые как применённые
```

Скрипт проверяет каждую миграцию по опорному объекту — таблице или колонке, —
показывает таблицу «в базе / в журнале» и по флагу `--apply` дописывает
недостающие строки в `payload_migrations`. Схему и данные он не трогает
вообще: единственная запись — строки журнала. После этого `payload migrate`
применит только то, чего в базе действительно нет.

Первое, что печатает скрипт, — замаскированная строка подключения. Прочитайте
её: команда работает с той базой, на которую указывает `DATABASE_URI`,
и перепутать локальную с продом здесь стоит дорого.

Две ситуации скрипт не чинит и говорит об этом прямо: миграция записана
в журнале, но её объектов в базе нет, и применённая миграция стоит после
неприменённой. И то и другое означает, что история сложнее, чем «схему создал
push», — додумывать за человека тут нельзя.

Добавили новую миграцию — допишите строку в `MIGRATIONS`
в `src/scripts/migrate-baseline.ts`, иначе скрипт о ней не узнает.

### Сам сид

Сид наполняет схему тем же набором, что и локально: 7 организаций,
8 пользователей, справочники, стада, техники, осеменения, контрольные дойки,
отёлы, события здоровья, события, документы, пакеты загрузки и файл протокола
ошибок к одному из них.

Животных создаётся 579:

| Группа | Записей | Видны в книге |
| --- | --- | --- |
| Быки-производители | 12 | да |
| Коровы и тёлки | 168 | да |
| Именованные предки первых трёх колен | 12 | нет, `archived: true` |
| Служебные предки глубоких колен (4–9) | 386 | нет, `archived: true` и `publicVisible: false` |
| Эталонная карточка «Поляна» | 1 | да |

В книге при этом видно около 130 записей. Архив исключён из всех списков
и счётчиков, поэтому 398 записей предков в выдачу не попадают, а из остальных
часть закрыта от анонимного просмотра.

Отдельная оговорка про итоговый лог: в конце сид печатает «животных: 181».
Это коровы, быки и «Поляна» — записи предков он в этот счёт не берёт.
Три числа (579, 181 и примерно 130) описывают разные вещи и путают,
если не знать, чем они отличаются.

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
PAYLOAD_DB_PUSH=false \
SEED_CONFIRM=1 \
npm run seed
```

Три детали, все важные:

- `DATABASE_URI` указывается **перед** командой — тогда переменная действует
  только на этот запуск и ваш локальный `.env` не трогается.
- `PAYLOAD_DB_PUSH=false` обязателен. Без него скрипт запустится в режиме
  разработки и попробует править схему прод-базы на лету, сравнивая её
  с конфигом. Схема там уже создана миграциями, и это лишний риск.
- `SEED_CONFIRM=1` нужен, если в базе уже есть животные: без него сид
  остановится с ошибкой и кодом возврата 1. Это предохранитель — сид
  начинается с полной очистки, и подтверждение требуется явно.

Скрипт **очищает** коллекции животных, воспроизводства, пользователей,
организаций и справочники перед наполнением. На пустой прод-базе это ничего
не значит, но если вы уже успели завести там настоящие записи — не запускайте.

## Способ 2. Перенести ровно вашу локальную базу

Нужен, если в локальной базе есть правки, которых нет в сиде.

```bash
# 1. Снимок локальной базы
pg_dump --no-owner --no-privileges --clean --if-exists \
  -d plemkniga -f ~/plemkniga-dump.sql

# 2. Заливка на прод
psql "postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
  -f ~/plemkniga-dump.sql

# 3. Отметить применёнными ВСЕ миграции — иначе Payload при старте
#    попробует создать таблицы заново
DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
npm run migrate:baseline -- --apply
```

Третий шаг обязателен. Локальная база строилась режимом push, поэтому таблицы
`payload_migrations` в ней либо нет, либо она пустая. Перенеся такую базу
на прод, вы получите полную схему, о которой Payload не знает, — и он попробует
применить поверх существующих таблиц все миграции подряд, начиная с первой.

Отмечать нужно весь список из `src/migrations/index.ts`, а не одну базовую
миграцию: пропущенная миграция будет применена при старте и упадёт
на `column ... already exists`. Скрипт берёт список сам и проверяет каждую
миграцию по факту наличия объектов в базе — руками перечислять их больше
не нужно. Без `--apply` он только показывает расхождения, и запускать его
для проверки безопасно в любой момент.

Если после переноса приложение жалуется на уникальный индекс по `uuid`:

```bash
DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
npm run repair:uuid
```

## Углубить родословную, ничего не удаляя

Сид — наполнение пустой базы: он начинается с полной очистки. На работающей
системе такой запуск уничтожает данные, и это уже случалось. Если нужно
только достроить родословную вглубь, чтобы посмотреть разбор до девятого
колена, сид не нужен:

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
  npm run pedigree:deep -- 3662217000196.00 9
```

Аргументов два:

| Аргумент | Значение |
| --- | --- |
| первый, обязательный | индивидуальный номер или id животного |
| второй, необязательный | глубина в коленах: по умолчанию 9, больше 12 не берётся |

Скрипт откажется работать в двух случаях: если у животного не заполнены оба
родителя (достраивать не от чего — вверх он идёт по существующим связям)
и если не заполнен владелец (служебные записи создаются от его имени,
иначе они повиснут ничьими).

Дальше скрипт идёт вверх по уже существующим связям и дописывает недостающих
предков служебными записями. Номер служебной записи — `ANC-<колено>-<индекс>`,
где индекс трёхзначный с ведущими нулями: `ANC-4-000`, `ANC-9-137`.
По этому номеру скрипт и узнаёт своих: повторный запуск ничего не дублирует.
Записи помечены признаком «в архиве». Он ничего не удаляет и не
перезаписывает: у животных, где родители уже проставлены, связи остаются как
есть.

Служебные записи не показываются ни в книге, ни в «Моих животных» — архив
исключён из списков. Открыть их можно только по ссылке из таблицы предков.

У сида теперь есть предохранитель: если в базе уже есть животные, он
остановится и потребует `SEED_CONFIRM=1`. Заодно покажет, к какой базе
подключился, — перепутать локальную строку с прод-строкой проще, чем кажется.
