# Перенос демонстрационных данных на прод

Два способа. Первый проще и почти всегда достаточен.

---

## Способ 1. Запустить сид против прод-базы (рекомендую)

### Сначала — миграции

Сид запускается локальным кодом против удалённой базы. Код знает про все поля
последнего коммита, база — только про те, что создали применённые миграции.
Если между ними разрыв, сид падает ещё на очистке:

```
error: column animals.for_sale does not exist
```

Это не поломка сида: на проде просто нет колонки, которую добавила миграция,
до неё не дошедшая. `PAYLOAD_DB_PUSH=false` (и правильно) не даёт скрипту
дописать колонку самому.

Миграции на прод попадают двумя путями — сами при старте контейнера после
деплоя (`prodMigrations` в конфиге) или вручную, не дожидаясь деплоя:

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
npm run payload migrate
```

Команда идемпотентна: применённые миграции пропускаются, применяются только
новые. Порядок для нового кода всегда один — `git push` → деплой (или
`payload migrate` вручную) → сид.

### Сам сид

Сид наполняет схему тем же набором, что и локально: 7 организаций,
8 пользователей, 193 животных (из них 132 открыты для анонимного просмотра),
справочники, осеменения, контрольные дойки, пакеты загрузки.

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
PAYLOAD_DB_PUSH=false \
npm run seed
```

Две детали, обе важные:

- `DATABASE_URI` указывается **перед** командой — тогда переменная действует
  только на этот запуск и ваш локальный `.env` не трогается.
- `PAYLOAD_DB_PUSH=false` обязателен. Без него скрипт запустится в режиме
  разработки и попробует править схему прод-базы на лету, сравнивая её
  с конфигом. Схема там уже создана миграциями, и это лишний риск.

Скрипт **очищает** коллекции животных, воспроизводства, пользователей,
организаций и справочники перед наполнением. На пустой прод-базе это ничего
не значит, но если вы уже успели завести там настоящие записи — не запускайте.

## Способ 2. Перенести ровно вашу локальную базу

Нужен, если в локальной базе есть правки, которых нет в сиде.

```bash
# 1. Снимок локальной базы
pg_dump --no-owner --no-privileges --clean --if-exists \
  -d plemkniga -f ~/plemkniga-dump.sql

# 2. Заливка на прод
psql "postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
  -f ~/plemkniga-dump.sql

# 3. Отметить миграцию применённой — иначе Payload при старте
#    попробует создать таблицы заново
psql "postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
  -c "INSERT INTO payload_migrations (name, batch, created_at, updated_at)
      SELECT '20260814_195548', 1, now(), now()
      WHERE NOT EXISTS (SELECT 1 FROM payload_migrations WHERE name = '20260814_195548');"
```

Третий шаг обязателен. Локальная база строилась режимом push, поэтому таблицы
`payload_migrations` в ней либо нет, либо она пустая. Перенеся такую базу
на прод, вы получите полную схему, о которой Payload не знает, — и он попробует
применить первую миграцию поверх существующих таблиц.

Если после переноса приложение жалуется на уникальный индекс по `uuid`:

```bash
DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
npm run repair:uuid
```

## Углубить родословную, ничего не удаляя

Сид — наполнение пустой базы: он начинается с полной очистки. На работающей
системе такой запуск уничтожает данные, и это уже случалось. Если нужно
только достроить родословную вглубь, чтобы посмотреть разбор до девятого
колена, сид не нужен:

```bash
cd ~/plemkniga

DATABASE_URI="postgresql://gen_user:ПАРОЛЬ@194.87.143.100:5432/plemkniga_dp?sslmode=require" \
  npm run pedigree:deep -- 3662217000196.00
```

Аргумент — индивидуальный номер или id животного. Скрипт идёт вверх по уже
существующим связям и дописывает недостающих предков служебными записями
(`ANC-колено-номер`, признак «в архиве»). Он ничего не удаляет и не
перезаписывает: у животных, где родители уже проставлены, связи остаются как
есть. Повторный запуск ничего не дублирует.

Служебные записи не показываются ни в книге, ни в «Моих животных» — архив
исключён из списков. Открыть их можно только по ссылке из таблицы предков.

У сида теперь есть предохранитель: если в базе уже есть животные, он
остановится и потребует `SEED_CONFIRM=1`. Заодно покажет, к какой базе
подключился, — перепутать локальную строку с прод-строкой проще, чем кажется.
