# Племенная книга

**Аналитическая надстройка над существующей инфраструктурой молочной фермы.**
Информационная система учёта племенной ценности КРС голштинской породы:
собирает фенотип и генотип из систем, которые уже работают в хозяйстве,
хранит племенную оценку в сопоставимом виде и превращает её в конкретную
инструкцию по подбору пар.

Расчёт самой оценки — впереди: сегодня система принимает EBV и gEBV извне
и хранит их парой «прогноз + достоверность». Что для собственного расчёта
недостаёт, разобрано в разделе [«Как считается ИПЦ»](#как-считается-ипц).

Разрабатывается для Ассоциации производителей КРС голштинской породы.

---

## Проблема, которую решаем

Главное возражение зоотехника на любую новую систему — «нам придётся вносить всё
дважды». Оно справедливо: данные о стаде уже лежат в DairyComp 305, DelPro,
UNIFORM-Agri или AfiFarm, результаты контрольных доек приходят из лаборатории,
генотипы — из сервис-лаборатории в виде файлов с чипа. Система, которая требует
повторного ввода, не приживается независимо от качества аналитики.

Поэтому продукт спроектирован не как ещё одна система управления стадом,
а как слой поверх них:

```
   системы управления стадом            лаборатории              чипы
   DairyComp · DelPro · UNIFORM          качество молока      Illumina · Thermo
   AfiFarm                               ДНК-тесты            PED/MAP · VCF
         │                                     │                    │
         └──────────────┬──────────────────────┴────────────────────┘
                        ▼
              ┌───────────────────────┐
              │   Племенная книга     │  единый идентификатор животного
              │  фенотип + генотип    │  родословная и достоверность данных
              │  оценка и подбор пар  │  племенная ценность и индексы
              └───────────┬───────────┘
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
  ФГИАС ПР          ВетИС «Хорриот»    зоотехник хозяйства
  (племресурсы)     (маркирование)     подбор пар, свидетельства
```

Ферма продолжает работать в привычной программе. Система забирает оттуда данные,
сводит их с племенной оценкой и происхождением и возвращает решение — какого быка
на какую корову.

## Три продуктовых акцента

### 1. Интеграционный слой: API First ◐ / ○

Данные приходят к нам, а не вводятся заново.

- **Системы управления стадом** — DairyComp 305, DelPro, UNIFORM-Agri, AfiFarm.
  Важная деталь, которую стоит знать до начала переговоров: **публичного REST API
  нет ни у одного из четырёх вендоров**. Интеграция строится адаптерами —
  через штатные выгрузки, чтение резервных копий БД и партнёрские соглашения
  (у VAS это отдельный Data Release Agreement, где владельцем данных признаётся ферма).
  Исключение — UNIFORM-Agri: у него подтверждена реализация стандарта ICAR ADE,
  и именно этот стандарт мы берём как целевой контракт обмена.
- **Лаборатории качества молока** — контрольные дойки, жир, белок, соматические
  клетки, мочевина. Формат обмена — ICAR ADE.
- **Генотипирование** — файлы с чипов Illumina и Thermo Fisher в PED/MAP, VCF
  и Illumina FinalReport.
- **Государственные реестры** — ФГИАС ПР (племенные ресурсы) и ВетИС «Хорриот»
  (маркирование и учёт). Подробности и правовые сроки — в [docs/standarty.md](docs/standarty.md).

### 2. Модуль подбора пар ◐

Значение gEBV само по себе — это аналитика. Ценность появляется, когда система
говорит: этого быка на эту корову.

- **Инбридинг-контроль.** Сейчас работает расчёт по родословной (формула Райта).
  Спроектирован геномный инбридинг **F_ROH** — по суммарной длине протяжённых
  участков гомозиготности; он честнее показывает реальную гомозиготность,
  чем родословная, особенно когда родословная неполная.
- **Летальные гаплотипы.** Проверка сочетания «носитель × носитель» по HH1–HH7,
  HCD, HMW, брахиспине, а также по CVM, BLAD и DUMPS. Такое сочетание блокируется
  до подбора, а не обнаруживается после отёла.
- **Автоматическое закрепление быков.** Формирование пар под цели конкретного
  хозяйства: например, поднять белок, не потеряв форму вымени, при ограничении
  на инбридинг потомства и на число доз одного быка.

### 3. Настраиваемый пользовательский индекс ◐

Крупный клиент задаёт собственные веса экономической значимости признаков —
и рейтинг животных пересчитывается под его экономику:

| Группа признаков | Пример веса |
| --- | --- |
| Белок и жир | 40% |
| Здоровье вымени и фертильность | 30% |
| Продуктивное долголетие | 20% |
| Экстерьер и крепость конечностей | 10% |

Индекс должен считаться по стандартизованным оценкам, чтобы признаки в разных
единицах можно было складывать. Замысел — показывать не только новый рейтинг,
но и **ожидаемый коррелированный отклик**: что произойдёт с признаками, которым
клиент веса не дал. Это защита от однобокой селекции — набор весов, дающий
быстрый рост удоя ценой фертильности, виден до того, как хозяйство закажет семя.

Ни весов, ни пресетов, ни стандартизации в коде пока нет. Чего не хватает,
чтобы это заработало, — ниже, в разделе [«Как считается ИПЦ»](#как-считается-ипц):
пользовательский индекс — не отдельная формула, а профиль весов поверх общего
механизма расчёта, которого сейчас тоже нет.

Подробный разбор всех трёх акцентов — [docs/pozicionirovanie.md](docs/pozicionirovanie.md).

## Domain Logic & Data Model ●

Ядро системы — граф животных с событиями и оценками.

```
organizations ──< herds ──< animals >── users (автор записи)
                              │
                              ├──< calvings          отёлы и межотельный цикл
                              ├──< inseminations ──> animals (бык)
                              ├──< milk-tests        контрольные дойки
                              ├──< health-events     здоровье
                              ├──< events            лента событий
                              └──< documents ──> media

organizations ──< data-submissions ──> media (протокол ошибок)
organizations ──< access-requests ──> animals (запрос доступа к закрытой карточке)

справочники НСИ: breeds, lines, breeding-categories, breeding-classes,
animal-purposes, disposal-reasons, coat-colors, blood-groups,
reproduction-methods, semen-types, insemination-results,
dna-test-types, haplotype-types, health-event-types, technicians
```

Ключевые сущности:

| Сущность | Что описывает |
| --- | --- |
| **Animal** | идентификация (GUID, инд. номер, бирка, чип), пол, порода, владелец, стадо, уровень достоверности, флаги публичности |
| **Pedigree** | связи `father` / `mother`, дерево на 3 ряда предков, коэффициент инбридинга, разметка источников инбридинга |
| **Phenotype Record** | контрольные дойки, отёлы, осеменения, здоровье, экстерьер — каждый факт с датой, источником и автором |
| **Lactation Curve** | массив лактаций: удой за лактацию и за 305 дней, жир и белок в % и кг, дойные дни, соматические клетки |
| **Genotype SNP** | ◐ генотип животного: чип, число маркеров, call rate, ссылка на исходный файл, набор вызовов по маркерам |
| **Evaluation** | ИПЦ и признаки в виде пары «прогноз + достоверность R,%» — форма, готовая принять EBV и gEBV |
| **AccessRequest** | обращение к владельцу закрытой записи: цель, сообщение, решение хозяйства с датой и автором |

Полное описание сущностей, валидаций и уровней достоверности —
[docs/model-dannyh.md](docs/model-dannyh.md).

## Genomic Pipeline ◐ / ○

Конвейер обработки геномных данных спроектирован в пять ступеней:

1. **Приём** — PED/MAP, бинарный BED/BIM/FAM, VCF, Illumina FinalReport;
   приведение аллелей к единой конвенции (TOP/BOT, Plus/Minus и Forward — три
   разные схемы, и смешивать их нельзя) и к единой сборке генома.
2. **Контроль качества** — call rate по образцу и по маркеру, MAF, отклонение
   от Харди–Вайнберга, менделевские конфликты «родитель–потомок».
3. **Импутация** — приведение чипов разной плотности к общей панели;
   в молочном скотоводстве применяются FImpute, Beagle и Minimac.
4. **Матрицы родства** — A по родословной и G по маркерам, их согласование.
5. **Single-Step GBLUP** — объединение A и G в одну матрицу H, чтобы
   генотипированные и негенотипированные животные оценивались совместно.

Конкретные пороги, формулы, форматы и подводные камни (включая то, почему
координаты SNP с разных чипов нельзя сравнивать без liftover) —
[docs/genomnyy-konveyer.md](docs/genomnyy-konveyer.md).

Честно о статусе: сегодня в системе есть **форма для хранения результата
оценки**, но не сам расчёт. Значения ИПЦ приходят извне. Геномный конвейер —
следующий крупный этап, и он требует не только кода, но и накопленной
референс-популяции.

## Как считается ИПЦ

Поле `ipc` в карточке — по-прежнему хранимое число: его привозят извне вместе
с оценками признаков. Рядом появился расчёт — `src/lib/breeding-index.ts`,
который собирает индекс из тех же оценок по заданному профилю весов.

Индекс собирается из оценок по отдельным признакам, приведённых к одной шкале:

```
ИПЦ = Σ  wᵢ · (EBVᵢ − μᵢ) / σᵢ  · масштаб
```

Из трёх составляющих в системе есть только первая:

| Составляющая | Что это | Состояние |
| --- | --- | --- |
| **EBVᵢ** | оценка по признаку: удой, жир и белок в кг, продуктивное долголетие, здоровье вымени, лёгкость отёла, фертильность, композиты экстерьера | ● Хранится парой «прогноз + R» |
| **μᵢ, σᵢ** | среднее и генетическое стандартное отклонение по референтной группе | ● Таблица `TRAIT_BASE`, параметры из Net Merit 2025 в метрических единицах; собственной базы Ассоциации пока нет ○ |
| **wᵢ** | веса: селекционные (проценты влияния) или экономические (рублей на единицу) | ● Профили в коде; интерфейс настройки ◐ |

Без базы сравнения складывать килограммы молока с баллами вымени нельзя:
получится сумма несопоставимых величин. База пересматривается — в мире это
делают раз в пять лет, — поэтому её версия хранится рядом с результатом.

Формулы достоверности и процентиля, таблица параметров, профили весов
и три готовых профиля под узкое место хозяйства —
[docs/indeks-plemennoy-cennosti.md](docs/indeks-plemennoy-cennosti.md).

Два соседних числа в карточке требуют того же:

- **R, %** ● — достоверность оценки: `R = n / (n + k)` по дочерям,
  `R = n·h² / (1 + (n−1)·rep)` по собственным лактациям, четверть суммы
  достоверностей родителей, объединение как независимых источников.
- **Процентиль** ● — место в группе сравнения (порода и год рождения),
  доля со значением ниже плюс половина доли равных.

Что осталось: хранить профили в базе, дать интерфейс их настройки, вывести
колонку индекса в книгу и записывать результат вместе с версией базы —
иначе через полгода нельзя объяснить, откуда взялось число в документе.

## Standards & Compliance ◐ / ○

| Стандарт | Что берём | Статус |
| --- | --- | --- |
| **ICAR ADE** (adewg/ICAR, релиз 1.5.1 от 10.12.2025, OpenAPI 3.1) | целевой контракт обмена фенотипом и данными доения | ◐ |
| **ICAR Guidelines Section 2** (Cattle Milk Recording, июнь 2023) | правила контрольных доек и расчёт удоя за 305 дней методом TIM | ◐ |
| **ICAR Guidelines Section 4** (DNA Technology) | пороги проверки происхождения по SNP | ◐ |
| **ICAR Guidelines Section 10** + ISO 11784/11785 | электронная идентификация животных | ◐ |
| **ICAR Certificate of Quality** (Section 8) | ориентир качества для Ассоциации как организации-члена | ○ |
| **Регламент (ЕС) 2016/1012** | форма зоотехнического сертификата для торговли | ◐ |
| **ФЗ № 454-ФЗ, ПП № 1741 и № 1742** | обязательная регистрация в ФГИАС ПР с 01.03.2026 | ○ |
| **ФЗ № 221-ФЗ, ПП № 550, приказ Минсельхоза № 832** | маркирование и учёт, ВетИС «Хорриот» | ○ |

Модели лактационных кривых — Wood, Wilmink и Ali-Schaeffer — с формулами
и областью применения описаны в [docs/standarty.md](docs/standarty.md).
Там же — важное уточнение о порогах проверки происхождения: ICAR задаёт их
**в процентах конфликтующих маркеров**, а не в абсолютном числе несовпадений.

## API Interfaces ● / ○

Поверх модели данных уже работает автоматический REST и GraphQL
(Payload CMS): `/api/animals`, `/api/inseminations`, `/api/milk-tests`,
`/api/data-submissions` и так далее, с фильтрами, пагинацией и правами доступа.

Спроектированы, но не реализованы:

- эндпоинты приёма фенотипа в форме ICAR ADE;
- приём файлов генотипирования с асинхронной обработкой и протоколом QC;
- исходящий обмен с ФГИАС ПР и ВетИС «Хорриот»;
- публичная страница проверки племенного свидетельства по QR.

Контракты, схемы запросов и модель аутентификации — [docs/api.md](docs/api.md).

## Быстрый старт

Нужен Node не ниже 22.12 (`engines` в `package.json`) и PostgreSQL.

```bash
cp .env.example .env          # DATABASE_URI, PAYLOAD_SECRET, NEXT_PUBLIC_SERVER_URL
npm install
npm run generate:types        # типы Payload → src/payload-types.ts
npm run seed                  # демо-данные: животные, организации, пользователи
npm run dev
```

### Где запускать служебные команды

**Не на боевом сервере.** Контейнер собирается без dev-зависимостей, а `tsx`
и `cross-env` лежат именно там — на проде любая из этих команд отвечает
`sh: cross-env: not found`. Это не поломка сборки: рабочему приложению они
не нужны, и тащить их в образ ради разовых операций незачем.

Правильный способ — запускать с машины разработчика, указав боевую базу
переменной окружения. Она перекрывает значение из `.env`:

```bash
DATABASE_URI='postgres://…прод…' npm run db:precheck
DATABASE_URI='postgres://…прод…' npm run backfill:index

# команды, которые много пишут, требуют ещё и явного подтверждения
SEED_CONFIRM=1 DATABASE_URI='postgres://…прод…' npm run seed:bulk -- --animals 280000
```

Каждый скрипт первой строкой печатает, к какой базе подключился, с замаскированным
паролем — прочитайте её прежде, чем отвечать на подтверждение. По сети команды
идут медленнее, чем локально: пакетная вставка — это тысячи обращений к базе,
и вместо трёх минут получаются десятки.

Исключение — `npm run payload migrate`: она встроена в запуск прода
(`prodMigrations`), применяется сама при старте контейнера, и вручную её
запускать не нужно.

#### Почему это однажды уронило прод

Запуск с машины разработчика идёт при `NODE_ENV=development`, а Payload по
одному этому признаку включает `drizzle push` — приведение схемы базы к текущему
конфигу на лету. Строку подключения он при этом не смотрит. То есть безобидная
на вид команда — пересчёт индекса, ревизия, выгрузка — правила боевую схему под
рабочую копию и оставляла в журнале миграций отметку `dev`. При следующем старте
прод видел её и спрашивал разрешения на миграции у контейнера, в котором некому
отвечать; контейнер вис на этом вопросе.

Теперь `push` дополнительно требует, чтобы база была локальной — петлевой адрес
или сокет (`isLocalDatabase` в `src/lib/db-url.ts`). Ошибиться этот признак может
только в безопасную сторону. Принудительно выключить — `PAYLOAD_DB_PUSH=false`.

Если отметка уже попала в боевой журнал, `npm run doctor` её покажет; убирается
она одной строкой:

```bash
DATABASE_URI='postgres://…прод…' npm run db:psql -- \
  -c "delete from payload_migrations where batch = -1"
```

Отметка опознаётся по `batch = -1`, а не по имени: имя `dev` — то, что кладёт
push сегодня, а Payload перед миграциями смотрит именно на номер пакета.
Заодно такой запрос обходит неприятность `npm run`: он вырезает кавычки внутри
аргументов, и `name = 'dev'` доходит до psql как `name = dev` — база отвечает
«column "dev" does not exist». Если литерал в запросе всё же нужен, передайте
запрос через stdin или мимо npm:

```bash
echo "delete from t where name = 'dev'" | npm run db:psql
npx tsx src/scripts/psql.ts -c "delete from t where name = 'dev'"
```

После этого — `DATABASE_URI='postgres://…прод…' npm run migrate:baseline`, чтобы
свериться, что журнал описывает то, что в базе на самом деле есть.

> В примерах многоточие — это место, куда подставляется настоящая строка
> подключения, а не часть команды. Для своей базы подставлять ничего не нужно:
> `npm run db:psql` возьмёт её из `.env` сам и первой строкой напечатает,
> к какой базе подключился.
